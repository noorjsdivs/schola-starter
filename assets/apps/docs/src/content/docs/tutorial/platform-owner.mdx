Before any school can open on Schola, someone has to run the platform. That
person is the **Super Admin**: they see every school, approve or reject new
applications, suspend schools and read the platform-wide audit log. The Super
Admin is not a member of any school — their home is the
[platform console](/features/platform/dashboard/) at <Route path="/platform" />.

Nobody can sign up as a Super Admin. The role is granted from the command
line by someone with access to the database, so it can never be claimed from
the web.

## What you'll do

- Learn how a real installation creates its first Super Admin.
- Sign in as the demo Super Admin and look around the platform console.

## Before you start

- The stack is running (`pnpm dev`) and you have run `pnpm seed` once.
- Browser profile: **Platform**.

<Tabs>
  <TabItem label="Demo (this tutorial)">
    `pnpm seed` already created the Super Admin **Sam Platform**,
    `superadmin@schola.example`, password `Schola@2026`. Use it — you do not
    need to run anything else.
  </TabItem>
  <TabItem label="A real installation">
    <Steps>

    1. Open `/signup`, stay on the **Personal account** tab and create your own
       account (first name, last name, email, password). It starts with no
       school — a *visitor* account.
    2. On the server, promote it:

       ```sh
       pnpm --filter @schola/api run grant-role -- --email you@yourschool.org --role super_admin
       ```

       The command needs `--email` and `--role`. Platform roles
       (`super_admin`, `user`) must **not** have `--school-id`; school roles
       (`school_admin`, `principal`, `teacher` …) require it. The account must
       already exist — the command never creates one.
    3. Sign in at `/login`. You land on <Route path="/platform" />. If you
       were already signed in, sign out and back in so the new role is picked up.

    </Steps>

    Promoting to `super_admin` also switches the account on (`isActive`),
    marks it a platform user, marks the email verified if it was not, and
    clears any login lock-out. The command writes a `user.role.grant` entry to
    the audit log with `actorRoleAtTime: "cli"`. Running it twice is harmless.
  </TabItem>
</Tabs>

<Aside type="caution" title="Keep grant-role on the server">
`grant-role` connects straight to the database named in your env files. Run it
only on a machine that should have that access, and never against a database
you do not mean to change.
</Aside>

## Check your work

- The top-left of the sidebar reads **Schola · Platform** and the bottom
  card reads **Sam · Super Admin**.
- <Route path="/platform/approvals" /> opens without an error. On a freshly
  seeded database it lists Riverside Academy and Lakeside Coaching Centre.

## If something goes wrong

- **"Invalid email or password."** — the seed has not run, or it ran with
  `--password`. Run `pnpm seed` (or `pnpm seed -- --reset` to start over).
- **You land on `/welcome` instead of `/platform`** — the account has no
  Super Admin role. On a real install, run `grant-role` again and sign out and
  back in.
- **"Account temporarily locked. Try again later."** — too many wrong
  passwords. Wait for the lock-out to expire, or run `grant-role` again,
  which clears it for a Super Admin.
